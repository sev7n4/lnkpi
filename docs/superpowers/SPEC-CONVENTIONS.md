# 规格书配图与写作规范（Spec Conventions）

状态：生效（2026-09-22，起于 WorkbenchShell + 扩图打样 spec 的实践沉淀）
适用：`docs/superpowers/specs/**`、`docs/superpowers/plans/**` 下的全部规格与计划文档
校验：`pnpm verify-spec-figures`（脚本 `scripts/verify-spec-figures.ts`，见 §8）

> 一句话：**图和文字同等重要，因此必须同样可维护、可 diff、可校验。** 能文本表达的图就内嵌，不能的才落附件，但两者都必须被索引、被引用、被验收。

---

## 1. 什么时候必须画图（判据，不是偏好）

出现以下任一情况，规格**必须**配图，否则视为规格不完整：

| 判据 | 典型场景 | 图类型 |
|---|---|---|
| **空间关系**说不清（谁在左/右/上/下、谁包含谁、多大） | 页面布局、面板分区、组件槽位、组件尺寸预算 | 视觉稿（§3.2） |
| **顺序/分支**说不清（先做 A 还是 B、失败了回哪） | 交互流程、状态机、退出链、守卫逻辑 | 结构图（§3.1） |
| **判据/规则**多于 2 层嵌套 | 工具接入判据、权限规则、优先级决策 | 结构图（§3.1） |
| **数据结构/契约**有字段或层级关系 | 注册契约、store 状态、IR 模型、ER | 结构图（§3.1） |
| **多个方案对比**且差异在结构而非措辞 | 方案 A vs B 的数据流 | 结构图（§3.1） |

反面判据（**不要**画图）：能用一张表和两句话讲清的、纯线性三步以内的、图与正文信息完全重复的。

---

## 2. 强制流程（写作时按此顺序）

1. **先写正文**（问题 / 判据 / 取舍），图是正文的锚点，不是装饰；
2. **按判据决定图的有无**（§1），再按 §3 路由选图形式；
3. **图的编号在文档内统一分配**，并在 §0 配图索引登记；
4. **每张图必须有图注**，且图注必须写"这张图说明了什么"，不是复述标题；
5. **正文必须引用图号**（`见 图 4`），让读者知道在哪用；
6. **收尾跑校验**：`pnpm verify-spec-figures`；
7. **评审时图与文字同权**：图错了 = 规格错了。

---

## 3. 图的两分法（路由规则）

**决策句：这张图能不能用文字结构（节点 + 关系 + 标签）无损表达？**

- 能 → **结构图**，用 Mermaid **内嵌**在 spec 里（首选，永远优先）
- 不能（需要真实的比例、位置、形状示意）→ **视觉稿**，用自绘 SVG 放 `assets/`

### 3.1 结构图（Mermaid 内嵌）

必须内嵌，不得导出成图片附件。理由：随文 diff、随文演进、无外部依赖、评审时能看到改动本身。

图类型路由表：

| 要表达的东西 | Mermaid 类型 |
|---|---|
| 流程 / 判据决策树 / 数据流 | `flowchart TD`（纵向）或 `flowchart LR`（横向） |
| 交互状态机（进入/退出/守卫） | `flowchart` + 判定节点（**不用** `stateDiagram`，渲染兼容性更稳） |
| 时序交互（请求/响应/回调） | `sequenceDiagram` |
| 字段/层级/包含关系 | `flowchart` + `subgraph`（容器） |
| 数据库/表结构 | `erDiagram` |
| 类/接口契约 | `classDiagram` |

书写硬约束（保证 GitHub 与本地渲染一致）：

- 节点标签一律用**引号包裹**：`A["文字"]`；含 `:` `/` `?` 的标签**必须**加引号；
- 判定节点用 `{"问题？"}`，出边带标签：`B -->|是| C`；
- **不要**用 `<br/>` 换行（兼容性差），改用 `/` 分隔或在节点内用短词；
- **不要**在标签里用 `()`（易被解析为形状语法），改用中文括号 `（）` 或 `/`；
- 一张图 **≤ 12 个节点**，超了拆图（拆成"总览 + 细节"两张）。

### 3.2 视觉稿（自绘 SVG 附件）

仅当图依赖**真实空间/比例/形状**时使用：页面布局稿、组件形状与尺寸、手柄/图标形态、设计板。

硬约束：

- **必须是自绘 SVG**，禁止贴截图（png/jpg/gif）——截图不可 diff、不可检索、体积大；
- 存放在**本文档同目录的 `assets/`** 下，用**相对路径**引用：`![图注](assets/xxx.svg)`；
- 命名：`<spec-slug>-<序号>-<名称>.svg`，例：`workbench-shell-and-outpaint-1-layout.svg`；
- **必须带编号标注**：在图上用 ①②③… 圈注关键区域，并在图下方或图内附**图例**说明每个编号是什么；
- **配色与字号遵循设计系统**（浅色主题：浅底 + 深字；正文 ≥11px；不使用渐变/阴影/发光）；
- SVG 根节点建议带 `font-family="-apple-system, 'PingFang SC', 'Microsoft YaHei', sans-serif"`，保证中文渲染；
- 自检边界：所有元素必须在 `viewBox` 内（脚本校验）。

## 4. 强制规则清单（R1–R8，与校验脚本一一对应）

| 规则 | 内容 | 级别 |
|---|---|---|
| **R1** | 像素级视觉稿必须是 `.svg` 且位于本文档 `assets/` 下；禁止 png/jpg/gif；能文本表达却做成附件的图报错 | 错误 |
| **R2** | 图必须编号（`图 1`、`图 2`…），文档内唯一、从 1 连续 | 错误 |
| **R3** | 每张图必须有图注（紧邻的 `*图 N · …*` 或 `**图 N · …**` 行） | 错误 |
| **R4** | 每张图必须在正文被引用（§0 索引与图注之外至少出现 1 次 `图 N`） | 警告 |
| **R5** | 含图的文档必须有 **§0 配图索引**章节，且索引列出全部图号 | 错误 |
| **R6** | 附件引用必须为相对路径且文件真实存在 | 错误 |
| **R7** | Mermaid 块非空，且首行为受支持的图类型关键字 | 错误 |
| **R8** | 视觉稿应有标注/图例（SVG 内 `text` 元素过少则提示） | 警告 |

**豁免机制**：文档内出现 `spec-figures: off`（配理由）时该文档跳过校验，仅打印提示。用于纯文字规格（如纯后端字段变更）。

## 5. 配图索引（§0，必需章节）

含图文档的第一章固定为 §0，形如：

```markdown
## 0. 配图索引（结构与视觉两类，均随本文档演进）

本文档的图分两类：**结构图**一律以 Mermaid 内嵌；**视觉稿**以 `assets/` 下的 SVG 附件承载（相对路径引用）。

| 编号 | 形式 | 内容 | 位置 | 用途 |
|---|---|---|---|---|
| 图 1 | 内嵌 Mermaid | 工具接入判据决策树 | §4.2 | 新工具接入自检 |
| 图 2 | SVG 附件 `assets/xxx-1-layout.svg` | 工作台整体布局 | §6 | 布局验收基准 |
```

「用途」列必须写**这张图在验收/决策里干什么**，不写"示意图"。

## 6. 规格骨架模板

```markdown
# <主题> 设计规格

状态：待评审（brainstorming 产出，YYYY-MM-DD）
前置：<相关规格文件>（已上线 / 待实现）
分支约定：实现走 feature 分支 + PR + squash merge。

## 0. 配图索引        ← 有图时必需；无图则写"本文档不含图（理由：…）"
## 1. 目标            ← 3 条以内，可验收
## 2. 范围（含明确不做）
## 3. 与既有规格的关系  ← 显式修订 / 显式推翻，避免新旧规格打架
## 4. 规范与判据        ← 可复用规则；后续同类需求直接套，不再重新设计
## 5. 架构与契约        ← 组件/接口/store 变更（配结构图）
## 6. 打样/主场景规格   ← 逐项可验收（配视觉稿）
## 7. 数据与状态变更
## 8. 纯函数与算法（含单测要求）
## 9. 文件级改动清单
## 10. 测试策略与验收标准（含目视验收）
## 11. 风险
## 12. 后续包 / 路线图  ← 本包外的东西也要登记，避免"隐性范围"
## 13. 配图规范自检     ← 跑 pnpm verify-spec-figures 的结果贴这里
```

## 7. 反模式清单（评审直接打回）

| 反模式 | 为什么不行 | 正确做法 |
|---|---|---|
| 贴竞品截图当设计稿 | 不可 diff、版权风险、尺寸失真 | 复刻为自绘 SVG，标注要素 |
| 把布局图导出成 PNG | 不可检索、体积大、改一处要重导 | 自绘 SVG |
| 图只在 IM/对话里，没进文档 | 评审期一过就丢失，后续包无从引用 | 图落 `assets/` + §0 索引 |
| Mermaid 标签不加引号 | 含 `:` `/` `?` 时渲染报错 | 一律 `A["文字"]` 包裹 |
| 一张图塞 20 个节点 | 读者看不懂，等于没有图 | 拆成总览 + 细节两张 |
| 图注写"架构图" | 零信息 | 写"这张图说明了什么、怎么用" |
| 图与正文重复 | 浪费评审注意力 | 正文讲判据，图讲结构 |
| 用图代替判据 | 图会过时，判据才是可执行规范 | 判据进正文，图只做锚点 |

## 8. 校验与 CI

本地（提交前必跑，与验证 4 条并列）：

```bash
pnpm verify-spec-figures          # 校验全部 spec；退出码非 0 = 有错误
pnpm verify-spec-figures --file docs/superpowers/specs/xxx.md   # 只校验单篇
```

脚本检查项 = §4 的 R1–R8：图号连续性、图注、§0 索引、附件存在性与格式、Mermaid 类型与空块、SVG 元素越界与标注提示。

**生效范围（不追溯）**：规范自 **2026-09-22** 起适用于**新增文档**；生效日之前的历史文档不追溯（存量 228 篇），但在**下次实质修改该文档时须补齐**配图规范。脚本默认只校验生效日之后的文档；`--all` 全量扫底用于批量补图。

**校验器自身必须验证**（否则等于没有）：新增/修改规则时，先造一份违规的负例文档跑一遍，确认**该报的错都报了、退出码为 1**，再删掉负例。首版验证结果：R1/R2/R3/R5/R6/R7 六类违规在负例中全部命中（7 个错误，退出码 1）。

接入 CI（本轮未接线，待评审通过后单独小包）：在 `ci.yml` 增加一个 docs job 跑该命令，使**规格类 PR 也受门禁**。注意 `ci.yml` 无 path 过滤，接线后所有 PR 都会跑；本命令为纯文本解析，耗时可忽略。

---

## 9. 规范自身的维护

- 本文件是规范源头；`scripts/verify-spec-figures.ts` 是其可执行部分，**两者必须同步演进**（加规则 = 先改本文件，再改脚本，再跑负例验证）；
- 新规则上线要求：能自动校验的必须自动校验；不能自动校验的（如"图注是否说清了用途"）进入评审清单，不硬凑脚本；
- 发现规范与实战冲突时：**先在实战里试跑一版，再回写规范**，不要预设一堆没人用的规则。
